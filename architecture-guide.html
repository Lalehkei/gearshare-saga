Architecture Reference

GearShare Saga

A peer-to-peer gear rental marketplace, built as seven Spring Boot services to teach microservices, message-driven architecture, and the saga pattern — the same rental-request flow wired up twice, once orchestrated and once choreographed, so the two styles can be compared directly instead of taken on faith.

java 21 spring boot 3.3 kafka postgres 7 modules
Why gear rental

Two acts, two lessons

A rental has a natural two-part structure, and each part teaches something different. Saga #1 — placing a request (booking → catalog → approval → payment) has three participants that must agree in sequence, one of whom is a human who might never respond. It's built both ways below. Saga #2 — fulfillment (handover reports pickup/return, payment captures or partially captures) is what makes payment holds versus captures concrete: saga #1 only ever authorizes a hold against a card; saga #2 is what turns it into real money, in full or reduced by a damage deduction.

Six services, one shared vocabulary

Saga #1, two ways

Orchestration vs. choreography

Same three participants, same outcome, two different ways of getting there. Run both from the same codebase with one environment variable and watch the log output diverge.

Orchestration orchestrator-service decides

  1. booking → orchestrator: RentalRequested
  2. orchestrator → catalog: HoldAvailabilityCommand
  3. catalog → orchestrator: CommandReply
  4. orchestrator → approval: RequestApprovalCommand
  5. approval → orchestrator: CommandReply
  6. orchestrator → payment: AuthorizePaymentCommand
  7. payment → orchestrator: CommandReply
  8. orchestrator → booking: RentalConfirmed

Choreography each service decides for itself

  1. booking → catalog: RentalRequested
  2. catalog → approval: AvailabilityHeld
  3. approval → payment: ApprovalGranted
  4. payment → booking: PaymentAuthorized + RentalConfirmed
  5. no coordinator exists — each hop is one service's own decision

On failure, the orchestrator walks backward through everything that already succeeded, in one place. In choreography, every participant that needs to compensate reacts to the same failure event independently — catalog releases its hold, approval marks its record moot, neither aware the other exists. By convention here, catalog-service (the first participant) is also the one that finally declares RentalCancelled, since it's always the last to finish unwinding.

Orchestration's extra trick: a saga-level timeout sweep catches a participant that never replies at all (its container is down, say) — distinct from approval-service's own per-request timeout for an owner who simply doesn't answer. Choreography has no natural place to put a check like this, since nothing watches the whole saga's clock centrally.

Saga #2, always choreographed

Fulfillment: pickup, return, capture

sequenceDiagram
    participant H as handover-service
    participant P as payment-service
    H->>P: PickupConfirmed
    Note over H: renter returns the item
    alt no damage
        H->>P: ReturnConfirmed
        P->>P: capture full amount
    else damaged
        H->>P: DamageClaimFiled
        P->>P: capture deduction, release remainder
    end

One participant reacting to one upstream service, in a straight line — not worth an orchestrator either mode. Real teams make this call constantly: recognizing when coordination overhead isn't worth it is as much part of learning this pattern as building it.

Run it

Two commands, two worlds

SAGA_MODE has no default on purpose — it drives which @Profile-gated beans activate, and the wrong one silently breaks the saga, so the compose file fails fast instead of guessing.

# orchestration mode (starts orchestrator-service too)
SAGA_MODE=orchestration docker compose --profile orchestration up --build

# choreography mode (no orchestrator container)
SAGA_MODE=choreography docker compose up --build

booking :8080 · catalog :8081 · approval :8082 · payment :8083 · handover :8084 · orchestrator :8085

Deterministic failure paths

Things to try

01

First-step rejection

Request item-005 (seeded permanently unavailable). The saga cancels before ever reaching approval — nothing to compensate.

02

Owner declines

POST {"approved": false} to the decision endpoint. Watch the item become available again.

03

Owner never answers

Don't call the decision endpoint. After 60s the sweep times it out and the saga unwinds the same way as a decline.

04

Card declined, full backward compensation

Use renterId: "renter-blocked". Both the hold and the already-granted approval get compensated.

05

Approval-service goes dark

Orchestration mode: stop the container mid-saga. After 90s the saga-level backstop compensates on its own.

06

Damaged return

Return with {"damaged": true, "deductionAmount": 15.00}. Payment goes to PARTIALLY_CAPTURED, remainder released.

Design notes

Holds vs. captures — PaymentSagaService

Saga #1 only ever authorizes; saga #2 is what actually moves money. Mirrors how real card processors handle hotel and car rentals.

Idempotent compensations — releaseAvailability, markMoot

Every compensating action is safe to call more than once, or when there's nothing to undo — a message can always be redelivered.

The ApprovalOutcomePublisher strategy — approval-service

Approval's outcome doesn't happen synchronously inside a listener — a human has to act. "Record the request" and "announce the decision" are decoupled, and where the decision goes is abstracted behind one interface with a mode-specific implementation.

Uniform backward compensation — SagaOrchestrationService

The orchestrator sends CancelApprovalCommand even when approval has nothing left to undo. Real orchestrators don't special-case that — they walk backward and trust each compensation to be a safe no-op.
